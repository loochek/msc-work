\section{Анализ существующих решений и постановка проблемы}
\label{sec:Chapter3} \index{Chapter3}

В предыдущем разделе были рассмотрены ключевые принципы, на которых основано построение современных сканеров уязвимостей. В этом разделе проводится обзор конкретных open-source сканеров, ставших де-факто стандартом отрасли~--- Trivy, Clair и Grype. Каждый из них реализует описанные принципы в той или иной форме, однако все они объединены общей моделью работы с container registry, в которой сосредоточен основной анализируемый в данной работе недостаток.

\subsection{Trivy}

\textit{Trivy}~\cite{trivy, trivydocs}~--- открытый сканер уязвимостей, разработанный компанией Aqua Security. На сегодняшний день Trivy является одним из наиболее популярных open-source решений в области сканирования уязвимостей в OCI-образах~--- в первую очередь благодаря простоте использования, обширному покрытию источников данных, активной поддержке и интеграциям. Он используется в качестве сканера по умолчанию в Harbor, поддерживается крупными CI/CD-платформами и регулярно фигурирует в обзорах безопасности контейнерной инфраструктуры.

Основной функционал Trivy сосредоточен в виде CLI-утилиты, написанной на языке Go. Помимо собственно сканирования OCI-образов, Trivy умеет анализировать файловые системы, репозитории git, артефакты Kubernetes и другие источники, однако наиболее распространенным сценарием его использования является сканирование контейнерных образов.

\subsubsection{Архитектура}

С точки зрения внутренней архитектуры Trivy организован модульно. Центральной концепцией являются \textit{анализаторы (analyzers)}~--- независимые модули, каждый из которых реагирует на определенные типы файлов и извлекает из них необходимую информацию. Все анализаторы перечислены в пакете \texttt{pkg/fanal/analyzer}, при этом каждый анализатор имеет:

\begin{itemize}
\item метод \texttt{Required(filePath, info)}, возвращающий, является ли данный файл интересным для анализатора;
\item метод \texttt{Analyze(...)}, осуществляющий собственно анализ файла и возвращающий извлеченную из него информацию.
\end{itemize}

Помимо анализаторов, Trivy поддерживает \textit{пост-анализаторы (post-analyzers)}, работающие на наборе уже подобранных файлов целиком (например, для разрешения зависимостей по содержимому нескольких связанных манифестов). Совокупная логика сводится к тому, что в процессе обхода файловой системы образа Trivy для каждого файла опрашивает все включенные анализаторы; если хотя бы один из них объявил файл нужным, файл передается на анализ.

\subsubsection{Источники уязвимостей}

В качестве базы уязвимостей Trivy использует репозиторий \texttt{trivy-db}, агрегирующий данные из множества источников: NVD~\cite{nvd}, дистрибутив-специфичных трекеров (Debian, Ubuntu, Red Hat, Alpine, SUSE, Oracle, Photon, Amazon Linux и др.), GitHub Advisory Database, OSV и других. Помимо общей \texttt{trivy-db}, для Java-артефактов используется отдельная база \texttt{trivy-java-db}, содержащая информацию о соответствии хешей JAR-файлов и их идентификаторов в Maven-репозитории. Обе базы распространяются в виде OCI-артефактов и автоматически обновляются перед каждым запуском, если не указано иное.

\subsubsection{Работа с registry}

При сканировании образа из container registry Trivy осуществляет следующие шаги:
\begin{enumerate}
\item получение манифеста образа из registry;
\item получение конфигурации образа;
\item проверка локального кеша на наличие уже проанализированных слоев~--- для каждого слоя, отсутствующего в кеше, требуется его получение из registry;
\item для каждого отсутствующего в кеше слоя~--- последовательная загрузка его блоба, распаковка gzip-потока и обход полученного tar-архива анализаторами;
\item агрегация результатов и сопоставление с базой уязвимостей.
\end{enumerate}

Важно отметить, что \textit{сам процесс получения слоя осуществляется целиком}: Trivy полностью скачивает блоб слоя из registry, после чего обходит его содержимое. Это происходит несмотря на то, что в подавляющем большинстве случаев анализаторам нужна лишь малая часть содержимого слоя~--- метаданные пакетных менеджеров и манифесты языковых зависимостей.

В коде самого Trivy наблюдается признание этой проблемы. Так, в пакете анализаторов имеется интерфейс \texttt{StaticPathAnalyzer}, который реализуется анализаторами с заранее известным фиксированным набором путей (apk, dpkg, rpm). Соответствующий метод \texttt{PartialStaticPaths()} возвращает совокупный список таких путей. Этот метод используется в режимах работы Trivy, когда сканер может частично загружать содержимое образа (например, при работе с локальной файловой системой). Однако языковые анализаторы (pip, npm, go, jar и др.) этот интерфейс не реализуют, поскольку их интересуют файлы с переменным расположением, выявляемые методом \texttt{Required}. По этой причине \texttt{PartialStaticPaths} оказывается неполноценным критерием выбора файлов, а в режиме работы с registry этот механизм не используется и слои скачиваются целиком.

\subsection{Clair}

\textit{Clair}~\cite{clair, clairdocs}~--- открытый сканер уязвимостей, разработанный компанией Red Hat. Исторически Clair был первым массово используемым open-source сканером и до сих пор остается важным игроком в индустрии. Clair используется в качестве сканера по умолчанию в реестре Quay.io от Red Hat и поддерживается во многих managed-registry. В отличие от Trivy, Clair изначально проектировался как сервис, а не CLI-утилита: его архитектура ориентирована на работу в режиме демона, к которому обращаются клиенты по HTTP API.

\subsubsection{Архитектура}

Архитектура Clair состоит из нескольких независимо запускаемых компонентов, каждый из которых отвечает за свою часть процесса сканирования:

\begin{itemize}
\item \textit{indexer}~--- компонент, отвечающий за инвентаризацию: принимает на вход манифест образа, скачивает его слои и формирует \textit{IndexReport}~--- список обнаруженных компонентов с метаданными;
\item \textit{matcher}~--- компонент, отвечающий за сопоставление с базой уязвимостей: на вход принимает дайджест ранее сформированного IndexReport, по которому формирует \textit{VulnerabilityReport}~--- итоговый отчет о найденных уязвимостях;
\item \textit{updater}~--- компонент, отвечающий за регулярное обновление базы уязвимостей из внешних источников;
\item \textit{notifier}~--- компонент, отвечающий за рассылку уведомлений при появлении новых уязвимостей, затрагивающих уже проиндексированные образы.
\end{itemize}

Помимо разделения на компоненты, важно отметить, что в Clair результат инвентаризации сохраняется в собственной базе данных (PostgreSQL): при повторном обращении к ранее проиндексированному образу инвентаризация заново не производится. Это позволяет Clair эффективно поддерживать сценарий, при котором появление новых записей в базе уязвимостей не требует повторного скачивания содержимого образов.

С точки зрения API Clair предоставляет следующие основные endpoint'ы:
\begin{itemize}
\item \texttt{POST /indexer/api/v1/index\_report}~--- запуск инвентаризации образа по его манифесту, который содержит ссылки на слои в виде HTTP URL;
\item \texttt{GET /matcher/api/v1/vulnerability\_report/<digest>}~--- получение отчета об уязвимостях для ранее проиндексированного образа.
\end{itemize}

Стоит отметить, что в Clair манифест образа на стороне клиента строится в особом виде, специфичном для Clair: вместо OCI-манифеста передается JSON, содержащий дайджест образа и список слоев, для каждого из которых указаны дайджест и HTTP URL для скачивания, а также произвольные заголовки (используемые, например, для передачи bearer-токена аутентификации в registry).

\subsubsection{Работа с registry}

При получении запроса на инвентаризацию indexer Clair проверяет, какие из перечисленных слоев уже были проанализированы ранее. Для всех неизвестных слоев он осуществляет скачивание содержимого по указанному в запросе URL и анализ полученного tar-архива. Как и в случае Trivy, скачивание производится \textit{целиком}: даже при наличии кеша для большинства слоев, отсутствие хотя бы одного из них в кеше приводит к необходимости полной загрузки этого слоя из registry. В целом модель работы аналогична Trivy: использование кеша на уровне слоев и полная загрузка отсутствующих в кеше слоев.

\subsection{Grype}

\textit{Grype}~\cite{grype}~--- открытый сканер уязвимостей, разработанный компанией Anchore. В отличие от Trivy и Clair, Grype не выполняет инвентаризацию самостоятельно, а ожидает на входе уже готовый SBOM, обычно сгенерированный родственным инструментом \textit{Syft}~\cite{syft}, тоже от Anchore. Эта связка~--- Syft + Grype~--- работает следующим образом:

\begin{itemize}
\item \textit{Syft} проводит инвентаризацию образа, генерируя SBOM в одном из поддерживаемых форматов (SPDX, CycloneDX, либо собственный <<lossless>>-формат Syft);
\item \textit{Grype} принимает на вход SBOM и сопоставляет его с базой уязвимостей, формируя итоговый отчет.
\end{itemize}

С точки зрения архитектуры Syft близок к Trivy: он также организован вокруг набора независимых анализаторов (catalogers), каждый из которых анализирует определенный тип артефакта. При сканировании образа Syft использует библиотеку \texttt{stereoscope}, обеспечивающую парсинг OCI-формата и распаковку слоев. Как и в случае Trivy и Clair, слои скачиваются и обрабатываются целиком. Кеш на уровне слоев в Syft отсутствует~--- каждый запуск сканирования образа подразумевает повторную загрузку всех слоев.

В качестве базы уязвимостей Grype использует собственный репозиторий \texttt{grype-db}, агрегирующий данные из множества источников~--- NVD, GitHub Advisory Database, дистрибутив-специфичных трекеров.

\subsection{Доступ к данным слоев и взаимодействие с container registry}

Все рассмотренные сканеры объединены общей моделью работы с container registry, которую можно описать следующим образом:

\begin{enumerate}
\item сканер получает манифест и конфигурацию образа из registry;
\item для каждого слоя, отсутствующего в локальном кеше, сканер скачивает его блоб \textit{целиком}~--- единственным HTTP-запросом на endpoint \texttt{/v2/<name>/blobs/<digest>};
\item полученный gzip-поток полностью разжимается, после чего обходится полученный tar-архив;
\item для каждого файла в архиве вызывается фильтрация анализаторов: если хотя бы один из них считает файл нужным, файл передается на анализ;
\item все необнаруженные файлы~--- то есть подавляющая часть содержимого слоя~--- остаются неиспользованными и в конечном итоге отбрасываются.
\end{enumerate}

Эта модель работы является следствием особенностей формата хранения слоев в OCI: содержимое слоя представлено tar-архивом, сжатым алгоритмом gzip с непрерывным потоком, что не позволяет читать произвольные файлы без полной распаковки потока до соответствующей позиции. С точки зрения registry слой~--- это просто блоб данных без какой-либо внутренней структуры, доступной registry, поэтому со стороны сервера ничего нельзя сделать для предоставления частичного доступа к содержимому. Соответственно, описанный недостаток является следствием не реализации конкретного сканера, а особенностей самого формата хранения слоев.

\subsubsection{Объем избыточно скачиваемых данных}

Чтобы оценить масштаб этой неэффективности, можно проследить следующий простой пример. Типичный образ Linux-приложения весом 200--500 МБ обычно состоит из нескольких слоев следующего вида:

\begin{itemize}
\item базовый Linux-слой (Ubuntu, Debian, Alpine, Fedora и т.п.)~--- 30--100 МБ;
\item слой с системными пакетами зависимостей~--- ещё 50--200 МБ;
\item слой с языковыми пакетами (pip, npm, go, jar и т.п.)~--- 50--300 МБ;
\item слой с приложением~--- от единиц МБ до сотен МБ в зависимости от типа приложения.
\end{itemize}

Из всего этого объема содержимое, представляющее непосредственный интерес для сканера, как правило, составляет:

\begin{itemize}
\item файл базы данных пакетного менеджера: 50--500 КБ;
\item манифесты языковых зависимостей: единицы или десятки КБ;
\item метаинформация о Go-модулях во вшитом виде~--- может варьироваться от единиц КБ до десятков МБ в зависимости от количества зависимостей.
\end{itemize}

То есть полезная часть содержимого, в общем случае, составляет лишь около 1--10\% от объёма всего образа. Иными словами, в типичном сценарии работы сканера через registry около 90\% скачиваемых данных в конечном итоге оказываются избыточными.

\subsubsection{Влияние на инфраструктуру}

В описанной модели сосредоточен ряд негативных эффектов с точки зрения как самого сканирования, так и инфраструктуры в целом:

\begin{itemize}
\item \textit{сетевой трафик}~--- объем данных, передаваемых между registry и сканером, в значительной части является избыточным, что увеличивает нагрузку на сеть и при этом дополнительно тарифицируется в случае managed-registry с оплатой за исходящий трафик;
\item \textit{дисковое пространство}~--- сканер вынужден временно хранить распакованное содержимое слоев на диске для проведения анализа, что особенно ощутимо в случае больших образов;
\item \textit{нагрузка на сам registry}~--- передача больших блобов требует ресурсов как сети, так и хранилища; в случае managed-registry это создает дополнительные операционные издержки;
\item \textit{время сканирования}~--- скачивание и распаковка слоев занимают значительную часть времени работы сканера, особенно при сканировании <<с холодного старта>>, когда локальный кеш пуст.
\end{itemize}

При интенсивном использовании container registry в рамках организации (десятки и сотни проектов, каждый из которых регулярно загружает в registry новые версии образов) эти эффекты накапливаются и становятся существенным фактором стоимости и пропускной способности всей инфраструктуры.

\subsection{Формулировка проблемы}

Проведенный обзор позволяет сформулировать основную проблему, рассматриваемую в данной работе:

\textit{Существующие сканеры уязвимостей, работающие со стороны container registry, для анализа образа загружают все его слои целиком, в то время как для проведения инвентаризации требуется лишь малая часть содержимого~--- метаданные пакетных менеджеров и манифесты языковых зависимостей. Это приводит к избыточному сетевому трафику, дисковым операциям и временным затратам, что особенно критично в сценариях интенсивной эксплуатации container registry.}

Решение этой проблемы естественным образом разделяется на две независимые подзадачи:

\begin{itemize}
\item обеспечить со стороны сканера возможность загружать из registry только необходимые для анализа файлы~--- то есть реализовать на стороне клиента \textit{ленивую загрузку} содержимого слоев;
\item обеспечить со стороны registry возможность отдавать содержимое слоев с гранулярностью, достаточной для эффективной ленивой загрузки.
\end{itemize}

В следующем разделе обсуждаются возможные подходы к решению этих подзадач и обосновывается выбор формата eStargz в качестве пути решения, наиболее совместимого с существующей инфраструктурой.
