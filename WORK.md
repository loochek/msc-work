#### Наработки:

---

Неформальная сводка:

* образ=корневая ФС контейнера

* состоит из набора диффов (**слоев**)

* Образ неизменяемый, потому что все провязано дайджестами

  * Но при обращении к реестру с именем и тегом может быть отдан другой образ - надо проверять ImageId, либо обращаться к манифесту по его дайджесту

Метаинформация сама по себе никак не поможет в установлении содержимого образа

---

Формально по документации:

**OCI образ** состоит из:

* Манифеста образа

* Image index (optional) - может задавать различные реализации образа (например в зависимости платформы и архитектуры) со ссылками на разные манифесты

* Слоев

* Конфигурации

**Дескриптор** ссылается на произвольные данные, может быть, с указанием источника. Состоит из:

* Типа данных, на которые он ссылается

* Размера

* Digest (контрольная сумма и уникальный идентификатор данных одновременно)

* Набора ссылок, по которым данные можно скачать (опционально)

**Манифест образа** состоит из:

* Дескриптора конфига образа

  * Digest конфига = **ImageID** (как я понял)

* Набора дескрипторов слоев (сами слои - tar или tar.gz архивы)

**Конфигурация образа** сотоит из:

* Всяких стандартных вещей, которые можно задать при создании образа

* Описания корневой файловой системы

  * Список контрольных сумм слоев (Layer DiffId)

**Container registry** определяет ручки скачивания и загрузки произвольных **манифестов** (манифест образа/image index) и **блобов** (бинарных данных слоев)

* /v2/<name>/manifests/<reference>

  * Name - имя образа (library/ubuntu)

  * Reference - тег или digest

* /v2/<name>/blobs/<digest>

Соответственно, пулл образа - запрос всех необходимых данных через эти ручки (манифест/конфиг/слои/…)

### Детальный анализ Trivy и Clair

#### Кеш Trivy

Trivy разделяет кеш на два уровня:

**Indexing (генерация SBOM) — кешируется персистентно:**
- Хранилище: **BoltDB** (`~/.cache/trivy/fanal/fanal.db`), бинарный файл
- Два bucket'а:
  - `blob` — `BlobInfo` на уровень слоя: пакеты, приложения, секреты, лицензии — фактически SBOM слоя
  - `artifact` — `ArtifactInfo` на уровень образа: архитектура, ОС, пакеты из RUN-инструкций
- Ключ кеша = SHA256 от `{ID слоя} + {версии анализаторов} + {версии политик} + {конфигурация}`
- Кеш персистентный и переживает перезапуски Trivy
- При обновлении Trivy версии анализаторов меняются → ключ меняется → автоматическая инвалидация

**Matching (сопоставление с CVE БД) — не кешируется:**
- Всегда выполняется заново против актуальной БД уязвимостей
- Это правильный дизайн: CVE БД обновляется ежедневно, результаты матчинга устаревают быстро

Redis, который я видел ранее — это опциональная альтернатива BoltDB для распределённого режима (клиент-сервер), а не замена. TTL для Redis настраивается пользователем.

Итого: у Trivy есть нормальный персистентный SBOM-кеш на уровне слоёв. Отсутствует только кеш результатов матчинга — и это по дизайну.

Ключевые файлы: `trivy/pkg/cache/fs.go`, `trivy/pkg/cache/key.go`, `trivy/pkg/fanal/artifact/image/image.go`

---

#### Кеш Clair

Clair архитектурно разделяет indexing и matching ещё более явно:

**Indexer:**
- Хранит `IndexReport` в **PostgreSQL**, ключ — digest манифеста
- `IndexReport` содержит: пакеты, дистрибутив, репозитории для каждого слоя (проприетарный формат, не SPDX/CycloneDX)
- Кеш персистентный, **TTL отсутствует** — результаты хранятся бессрочно
- Инвалидация через механизм `index_state`: indexer отдаёт ETag, представляющий хеш текущей конфигурации сканеров. При обновлении сканера ETag меняется — клиент обязан заново отправить манифест на индексирование
- Пересканирование — ответственность клиента (Quay, Harbor и т.д.), Clair сам его не инициирует

**Matcher:**
- Хранит **базу уязвимостей** (обновляется updater'ами из NVD, Alpine, Ubuntu и т.д.)
- Результаты матчинга **не кешируются** — каждый раз выполняются заново против актуальной БД
- HTTP Cache-Control headers (`matcher.cache_age`) — только advisory hint для клиента, не персистентный кеш

Итого: Clair персистентно кеширует именно SBOM (IndexReport), но не результаты матчинга. Политика инвалидации — через ETag, элегантно.

Ключевые файлы: `clair/indexer/service.go`, `clair/httptransport/indexer_v1.go`, `clair/initialize/services.go`

#### Взаимодействие с container registry и вопрос прямого доступа к blob storage

**Как оба сканера получают слои:**

1. Клиент (Harbor/Quay/что угодно) делает `GET /v2/{name}/blobs/{digest}` к registry
2. Harbor/Quay отвечают `307 Temporary Redirect` с presigned S3 URL
3. Go `http.Client` автоматически следует за redirect (поведение по умолчанию)
4. Данные слоя скачиваются **напрямую из S3**, минуя Harbor как прокси

Это подтверждено кодом Clair — в `clairctl/manifest.go` явный комментарий: *"The request is needed to follow any redirection chain that the server sends to a client"*, финальный URL берётся из `res.Request.URL` после редиректа.

Trivy аналогично — использует `google/go-containerregistry`, стандартный Go `http.Client`.

**Вывод: Harbor не является узким местом для передачи данных.** Слои скачиваются напрямую из S3. Мой изначальный тезис о "лишнем скачивании через Harbor" — неточен в части пропускной способности.

**Что остаётся проблемой:**

Tar-формат не поддерживает произвольный доступ (random access) — нет индекса файлов внутри архива. Поэтому для анализа слоя необходимо:
- Скачать весь tar-архив слоя целиком
- Распаковать gzip
- Последовательно обойти всё дерево файлов

"Прямой доступ к ФС registry" дал бы преимущество только если:
- Хранить индекс содержимого tar рядом с blob'ом (что позволило бы делать range requests на нужные файлы)
- Или хранить содержимое слоёв не в tar, а в формате с поддержкой random access

#### Какие файлы реально читаются из tar при индексировании

**Оба сканера читают крайне малую долю файлов слоя, но вынуждены скачивать весь tar целиком.**

Конкретные пути, которые ищут анализаторы:

| Пакетный менеджер | Файлы |
|---|---|
| dpkg (Debian/Ubuntu) | `/var/lib/dpkg/status`, `/var/lib/dpkg/status.d/`, `/var/lib/dpkg/info/*.md5sums` |
| apk (Alpine) | `/lib/apk/db/installed`, `/usr/lib/apk/db/installed` |
| rpm (RHEL/CentOS) | `/var/lib/rpm/Packages`, `/var/lib/rpm/rpmdb.sqlite` и варианты |
| Определение ОС | `/etc/os-release`, `/usr/lib/os-release`, `/etc/debian_version`, `/etc/alpine-release` |
| Python | `*.dist-info/METADATA`, `*.egg-info/PKG-INFO` |
| Java | `*.jar`, `*.war`, `*.ear` |

Из логов Clair видно: при скачивании слоя Ubuntu `size=80419840` (~80 МБ), а реально нужны лишь единицы килобайт пакетных метаданных.

**Ключевая находка в коде Trivy:**

Trivy имеет интерфейс `StaticPathAnalyzer` — анализаторы могут декларировать конкретные пути, которые им нужны:
- `dpkg` → `["/var/lib/dpkg/status", "/var/lib/dpkg/status.d", ...]`
- `apk` → `["/lib/apk/db/installed", "/usr/lib/apk/db/installed"]`
- и т.д.

**При сканировании локальной ФС** (`artifact/local/fs.go`) этот механизм **используется** — Trivy идёт только по нужным путям.

**При сканировании tar образа** (`artifact/image/image.go`, `walker/tar.go`) этот механизм **игнорируется** — tar читается последовательно целиком, и для каждого файла вызывается `Required()` у каждого анализатора.

Это архитектурный gap: возможность уже есть в коде, но не подключена к tar-walker'у.

Clair аналогично: claircore скачивает слой полностью, монтирует как `tarfs` и запускает все сканеры параллельно поверх него.

**Что нужно для sparse access:**
1. Tar-индекс — файл с byte offset'ами каждой записи внутри (сжатого) tar
2. Список нужных путей — берётся из `StaticPaths()` анализаторов
3. HTTP Range requests — скачиваем только нужные диапазоны байт из S3

Это конкретная, измеримая оптимизация: вместо 80 МБ скачиваем несколько сотен КБ.

**Ограничение:** gzip-сжатие tar делает random access нетривиальным — нужно либо хранить слои несжатыми (zstd с seekable format), либо хранить индекс с учётом gzip-блоков (zran-подход). В OCI допускается `application/vnd.oci.image.layer.v1.tar` (без сжатия) — но на практике везде используется `tar+gzip`.

Ключевые файлы:
- `trivy/pkg/fanal/analyzer/analyzer.go` — интерфейс `StaticPathAnalyzer`
- `trivy/pkg/fanal/walker/tar.go` — последовательное чтение tar (без использования StaticPaths)
- `trivy/pkg/fanal/artifact/local/fs.go` — пример использования StaticPaths для локальной ФС

### Анализ проблем и существующих решений

#### Проблема 1: Фоновое переиндексирование при обновлении сканера

**Вопрос:** если логика индексера обновилась, все старые SBOM невалидны. Нужно ли переиндексировать всё в фоне?

**Что уже реализовано в индустрии:**

| Решение | Подход к переиндексированию |
|---------|---------------------------|
| **Clair** | `VersionedScanner` + `index_state` ETag — клиент узнаёт об изменении и переотправляет манифесты. Но приоритизации нет |
| **Trivy** | Нет механизма обнаружения — версии анализаторов зашиты в ключ кеша, при обновлении старые записи просто не находятся |
| **Docker Scout** | Хранит SBOM-снапшот, при новых CVE матчит по нему без пересканирования. При обновлении анализатора — неизвестно |
| **AWS Inspector** | Continuous scanning: при появлении новой CVE переоценивает хранимый SBOM. Окно мониторинга 14-180 дней |
| **GCP Artifact Analysis** | Continuous analysis 30 дней после push, потом образ "стухает" |
| **Azure Defender** | Еженедельный rescan образов, которые пулились за последние 30 дней |

**Как часто обновляется логика индексера?** Раз в несколько месяцев (по changelog'ам ClairCore/Trivy). Это редкое событие.

**Thundering herd проблема:** при обновлении индексера все образы нужно переиндексировать одновременно. Решения:
- Clair: admin-команда для конкурентного переиндексирования
- Trivy Operator: `scanJobsConcurrentLimit` — throttling
- Никто не делает **приоритизацию по популярности слоёв**

**Вывод:** идея lazy retention / приоритизированного переиндексирования валидна, но это инкрементальная оптимизация, а не фундаментальный вклад. Разделение indexing/matching и персистентный SBOM-кеш — уже решённые задачи.

---

#### Проблема 2: Полное скачивание слоя ради нескольких файлов

**Вопрос:** оба сканера скачивают весь слой (~80 МБ для Ubuntu base) и распаковывают gzip, хотя реально нужны единицы КБ. Можно ли это оптимизировать?

**Механизмы random access к сжатым слоям — уже существуют:**

| Решение | Суть | Статус | Ломает DiffID? |
|---------|------|--------|----------------|
| **eStargz** (containerd) | Каждый файл — отдельный gzip member, JSON TOC в конце слоя | Работает с любым OCI registry, поддержка в BuildKit, CRI-O, Podman, nerdctl | **Да** |
| **zstd:chunked** (Red Hat) | Метаданные внутри zstd-потока | Экспериментальный, Fedora обсуждала переход по умолчанию | **Нет** |
| **AWS SOCI** | Внешний zTOC-индекс (zran-стиль) хранится как OCI artifact (Referrers API), **образ не модифицируется** | В продакшне на AWS Fargate/EKS | **Нет** |
| **Nydus ZRAN** (Alibaba/Dragonfly) | Внешний индекс для существующих gzip-слоёв | Поддерживает Harbor, Docker Hub, GHCR | **Нет** |

**Ключевая цифра:** Harter et al. (FAST '16) — 76% времени запуска контейнера уходит на скачивание образа, но реально используется только 6.4% данных.

Все эти решения разработаны для **lazy pulling** — ускорения запуска контейнеров. **Никто не применял их для selective vulnerability scanning.**

**Почему это важно для сканирования:**
- При lazy pulling нужно ~6.4% файлов слоя
- При сканировании нужно ещё меньше — буквально несколько конкретных файлов пакетных менеджеров (доли процента)
- В Trivy уже есть `StaticPathAnalyzer` — список нужных путей известен заранее
- Комбинация `StaticPaths()` + TOC из eStargz/SOCI позволяет скачать только нужные файлы через HTTP Range requests

**Вариант без модификации образов (SOCI-подход):**
- zTOC генерируется при push образа в registry
- Хранится как OCI artifact рядом с образом через Referrers API
- Сканер читает zTOC → определяет byte ranges нужных файлов → делает Range requests к S3
- Оригинальный образ не затрагивается

**Вариант с несжатыми слоями:**
- Хранить `application/vnd.oci.image.layer.v1.tar` (без gzip) — random access тривиален
- **Но:** ~3x увеличение стоимости хранения (медианная степень сжатия 3.2-3.5x по данным анализа Docker Hub, 167 ТБ данных)
- Непрактично для общего использования

**Компромисс — zstd seekable format:**
- zstd сжимает лучше gzip и значительно быстрее распаковывается
- Seekable format поддерживает random access нативно
- OCI спецификация v1.1 поддерживает `tar+zstd` как media type
- AWS показал 27% снижение времени запуска при переходе на zstd

#### Главный вывод: что реально ново

**Уже решено (не новизна):**
- Разделение indexing/matching — Clair, Docker Scout, все облачные провайдеры
- Персистентный SBOM-кеш с версионированием — Clair (`VersionedScanner` + IndexReport), Trivy (BoltDB + ключ с версиями анализаторов)
- Переиспользование результатов анализа общих слоёв — оба сканера делают по digest

**Неисследованное направление:**
- **Selective layer scanning** — использование file-level random access (eStargz TOC / SOCI zTOC) для скачивания **только файлов пакетных менеджеров** вместо всего слоя
- Комбинация Trivy `StaticPathAnalyzer` + SOCI zTOC / eStargz TOC → вместо 80 МБ скачиваем сотни КБ
- Никто не публиковал и не предлагал эту комбинацию (проверено: issues Trivy/Clair, академические статьи)

**Инкрементальные оптимизации (валидные, но не центральные):**
- Приоритизированное переиндексирование популярных слоёв при обновлении сканера
- Time-window filtering для ограничения объёма пересканирования (как у облачных провайдеров)

### Механизм слоёв и lazy pulling

#### OverlayFS: как работает композиция слоёв

```
mount -t overlay overlay \
  -o lowerdir=<layer3>:<layer2>:<layer1>,upperdir=<container-rw>,workdir=<scratch> \
  /merged
```

- **lowerdir** — read-only слои образа (до 128), от верхнего к нижнему
- **upperdir** — один read-write слой контейнера
- **workdir** — внутренний scratch для атомарных операций ядра
- **merged** — точка монтирования, видимая процессу в контейнере

**Чтение файла:** ядро ищет сверху вниз (upperdir → lowerdir'ы). Файл из нижнего слоя читается **напрямую с его inode** — без копирования, почти native по скорости.

**Изменение файла (copy-up):** при первой записи в файл из нижнего слоя ядро копирует **весь файл** в upperdir:
1. Попытка `vfs_clone_file_range()` (reflink — мгновенно на XFS/Btrfs)
2. Fallback на `vfs_copy_file_range()` чанками
3. Fallback на `do_splice_direct()`

Важно: 1 байт записи в 2 ГБ файл → copy-up 2 ГБ. Есть оптимизация `metacopy=on` — при изменении только метаданных (chmod) копируются только метаданные, данные подтягиваются при первом write.

**Удаление файла (whiteout):** в upperdir создаётся character device с major:minor=0:0 через `mknod()`. Для удаления содержимого директории — xattr `trusted.overlay.opaque=y`.

**Производительность:**
- Чтение из любого слоя — быстро (native inode delegation)
- Первая запись в файл нижнего слоя — медленно (copy-up пропорционален размеру файла)
- Lookup при большом количестве слоёв — деградирует линейно
- `stat()`-heavy нагрузки (`find`, `ls -lR`) — заметно медленнее с ростом числа слоёв

#### OCI whiteouts vs OverlayFS whiteouts

В tar-слоях OCI используется формат из AUFS (не из OverlayFS):

| Операция | В tar (OCI) | На ФС (OverlayFS) |
|----------|-------------|-------------------|
| Удаление файла `foo` | Файл `.wh.foo` (обычный файл) | Character device (0,0) через `mknod` |
| Удаление содержимого директории | Файл `.wh..wh..opq` | xattr `trusted.overlay.opaque=y` |

При распаковке runtime **конвертирует**: `.wh.X` → `mknod(path, S_IFCHR, 0)`, `.wh..wh..opq` → `setxattr()`. Создание character device требует `CAP_MKNOD`.

#### Стандартный (не-lazy) pull: пошагово

1. `GET /v2/` — проверка API
2. `GET /token?...` — аутентификация
3. `GET /v2/<name>/manifests/<tag>` — image index (multi-platform)
4. `GET /v2/<name>/manifests/<digest>` — манифест для конкретной платформы
5. `GET /v2/<name>/blobs/<config-digest>` — конфиг (JSON: env, entrypoint, diff_ids)
6. `GET /v2/<name>/blobs/<layer-digest>` × N — слои **параллельно** (3-4 потока), registry обычно отвечает 302/307 redirect на CDN/S3

Для каждого слоя containerd через snapshotter:
1. `Prepare(key, parent)` — создать active snapshot поверх предыдущего committed
2. Распаковать tar.gz в snapshot, конвертируя OCI whiteouts → OverlayFS whiteouts
3. `Commit(name, key)` — зафиксировать как immutable snapshot (имя = ChainID = `SHA256(parent_chainID + " " + diffID)`)

**Контейнер стартует только после скачивания и распаковки ВСЕХ слоёв.** Это фундаментальное ограничение стандартного pull.

#### Lazy pulling: суть

**Идея:** контейнер стартует, когда доступны **метаданные ФС** (имена, размеры, права), но содержимое файлов скачивается **по первому обращению**. FUSE-демон перехватывает `read()` и делает HTTP Range Request к registry.

**Когда файл скачивается:**
- При первом `read()` / `mmap()` к этому файлу
- Либо заранее, если попадает в prefetch-список

**Long tail проблема:** lazy pulling не устраняет скачивание — он перераспределяет его из pull time в runtime. Если приложению нужно много файлов при старте (Python с сотнями модулей, Java с jar'ами), суммарная задержка от множества мелких Range requests значительна.

Конкретные цифры (Grab, Airflow на eStargz): startup приложения **25 с** vs 5 с с обычным OverlayFS. Pull быстрый, но on-demand загрузка файлов при работе — медленная. SOCI при тех же условиях сохранил 5 с (за счёт aggressive background fetch).

**Ключевая цифра:** Harter et al. (FAST '16) — 76% времени запуска контейнера уходит на скачивание образа, но реально используется только 6.4% данных.

#### Решения lazy pulling: подробный разбор

##### eStargz (containerd/stargz-snapshotter)

**Формат:** каждый файл в tar сжат как отдельный gzip member. Валидно по RFC 1952 (конкатенация gzip members).

**TOC:** JSON-файл `stargz.index.json` — последний tar entry. Для каждого файла:
- `Name`, `Type` (dir/reg/symlink/hardlink/chunk), метаданные (uid, gid, mode, mtime)
- `Offset` — byte offset gzip member'а в blob'е
- `ChunkOffset` / `ChunkSize` — для больших файлов, разбитых на несколько gzip members
- `Digest` — SHA-256 целого файла, `ChunkDigest` — SHA-256 отдельного чанка

**Footer:** 47 байт в конце blob'а — пустой gzip member с Extra полем (SI1='S', SI2='G'), содержащим hex-encoded offset TOC + строку "STARGZ".

**Чтение файла:**
1. Range Request на последние 47 байт → offset TOC
2. Range Request на TOC JSON → вся структура ФС в памяти (имена, размеры, права — всё доступно)
3. При обращении к файлу → Range Request на gzip member по offset из TOC → декомпрессия одного файла

**Prefetch (landmark):**
- `ctr-remote images optimize` профилирует workload в sandbox, определяет файлы, нужные при старте
- Эти файлы перемещаются в начало архива, после них ставится `.prefetch.landmark`
- При запуске контейнера — **один** Range Request от 0 до landmark offset = bulk prefetch

**Верификация:** manifest содержит аннотацию `containerd.io/snapshot/stargz/toc.digest` → TOC содержит `ChunkDigest` для каждого чанка → цепочка доверия от подписи манифеста до отдельного файла.

**Overhead:** на несколько % больше стандартного tar.gz:
- Per-file gzip headers (~10+ байт каждый)
- Потеря кросс-файлового контекста сжатия (компрессор сбрасывается на каждом файле)
- Сам TOC JSON (растёт с количеством файлов)
- Опция `--estargz-min-chunk-size` — пакует мелкие файлы в один gzip member (грубее granularity, но меньше overhead)

**Совместимость:** полная обратная совместимость — валидный tar.gz, любой runtime распакует целиком. **Но ломает DiffID** (digest несжатого tar отличается из-за встроенного TOC entry).

**Runtime:** FUSE-демон `containerd-stargz-grpc`, proxy plugin для containerd snapshotter.

##### AWS SOCI (Seekable OCI)

**Ключевое отличие: образ НЕ модифицируется.** Индекс хранится отдельно как OCI artifact.

**zTOC** (генерируется для слоёв > 10 МБ, порог настраивается через `--min-layer-size`):
- **TOC** — таблица: файл → offset в **распакованном** tar
- **zInfo** — checkpoint'ы декомпрессора в формате FlatBuffers (binary). Техника из zran.c Марка Адлера: каждые ~4 МБ сжатых данных сохраняется состояние DEFLATE — 32 КБ sliding window + позиция в битовом потоке + таблицы Хаффмана

**Концепция span:** сжатый слой делится на span'ы по ~4 МБ между checkpoint'ами.

**Чтение файла:**
1. TOC → offset файла в распакованном tar
2. Маппинг на span, содержащий этот offset
3. Range Request на span (сжатые байты)
4. Инициализация DEFLATE-декомпрессора с checkpoint'а → распаковка до нужного offset'а → извлечение файла

**Waste:** до 4 МБ лишних данных на один файл (весь span). Уменьшение span → больше checkpoint'ов → больше overhead хранения (~32 КБ на checkpoint).

**Overhead хранения:** для 400 МБ слоя → ~100 span'ов → ~3.2 МБ zInfo. В целом zTOC — от нескольких сотен КБ до нескольких МБ на слой.

**Referrers API:** zTOC хранится как OCI Artifact:
- `artifactType: application/vnd.amazon.soci.index.v1+json`
- `subject` указывает на манифест образа
- Registry с Referrers API позволяет обнаружить индекс автоматически по digest образа

**Background fetch:** SOCI **сразу** начинает фоновое скачивание полного образа параллельно с работой контейнера. Чем дольше контейнер работает — тем больше файлов уже локально. Именно поэтому у Grab: SOCI = 5 с startup, eStargz = 25 с (eStargz без background fetch, только on-demand).

**Fallback:** если zTOC отсутствует или повреждён — обычный full pull. Graceful degradation.

**Порог эффективности:** по данным AWS, заметный выигрыш для образов > 250 МБ. Для образов < 250 МБ overhead FUSE setup может нивелировать выигрыш.

##### zstd:chunked (Red Hat / Podman)

**Формат:** zstd со **skippable frames** (magic `0x184D2A50`–`0x184D2A5F`). Любой zstd-декомпрессор молча пропускает эти фреймы → полная обратная совместимость. Внутри фреймов — TOC с метаданными.

**Это НЕ lazy pulling в FUSE-смысле — это selective/partial pull.** Файлы скачиваются при pull, не on-demand при runtime. Контейнер стартует после завершения pull, но pull значительно быстрее.

**Ключевая фишка — локальная дедупликация:**
1. При pull Podman читает TOC нового слоя (Range Request к концу blob'а)
2. Сканирует **все локальные слои** через `chunked-manifest-cache` (бинарный mmap-friendly индекс с SHA-256 каждого файла/чанка)
3. Файлы с совпадающим SHA-256 → hardlink или reflink с локального диска
4. Только отсутствующие файлы → Range Requests к registry

Цифры от Red Hat: для nginx/fedora **81% данных пропущено** благодаря локальной дедупликации.

**DiffID:** не ломается — метаданные в skippable frames не влияют на распакованный tar. (Были баги с этим, исправлены.)

**Преимущество zstd над gzip:** на 10-20% лучше сжатие + 3-5x быстрее декомпрессия. Частично компенсирует per-chunk overhead.

**Поддержка:** Podman, Buildah, Skopeo, CRI-O. **НЕ поддерживается** containerd/Docker для partial pull (они тянут целиком как обычный zstd).

##### Nydus (Dragonfly / Alibaba)

**Принципиально другой подход** — собственный формат RAFS вместо tar.

**Структура:**
- **Bootstrap** (metadata blob) — полное дерево ФС: имена, права, маппинг файлов на чанки данных. Суперблок в первых 8 КБ.
- **Data blobs** — content-addressable чанки по 1 МБ. Дедупликация **между разными образами** по content hash.

**Три режима runtime:**

| Режим | Механизм | Latency на операцию |
|-------|----------|-------------------|
| **FUSE** | userspace daemon `nydusd` | ~100-500 мкс |
| **virtiofs** | для VM-based изоляции (Kata) | сравнимо с FUSE |
| **EROFS over fscache** (Linux 5.19+) | in-kernel, без FUSE | ~10-50 мкс (~10x быстрее FUSE) |

EROFS path — **единственное** lazy pulling решение, работающее целиком в ядре. Нет FUSE context switch, после кеширования — почти native скорость.

**ZRAN mode** (для существующих gzip-образов без конвертации):
- `nydus-image` генерирует ZRAN-артефакт: checkpoint'ы DEFLATE + файловый TOC
- Хранится рядом как OCI artifact (аналогично SOCI)
- `nydusd` использует артефакт для lazy pull из **немодифицированного** gzip-слоя
- Образ не меняется, digest'ы сохраняются
- Доступен начиная с Nydus >= v2.2

**P2P:** интеграция с Dragonfly — peer-to-peer раздача чанков между нодами. Актуально для кластеров: если соседний узел уже скачал чанк, берём у него, а не из registry.

---

##### CRFS (Google) — оригинальный stargz (исторический контекст)

Proof-of-concept от Brad Fitzpatrick (Google). Та же идея: seekable tar.gz с индексом в конце. Заброшен в пользу eStargz, который добавил:
- Per-chunk верификацию (CRFS не мог проверить отдельные файлы — только весь слой целиком)
- Prefetch через landmark'ы (CRFS — только on-demand)
- RFC 1952-compliant footer (CRFS footer нарушал спецификацию gzip Extra field)

Репозиторий `github.com/google/crfs` фактически заброшен.

#### Сводная таблица lazy pulling решений

| | eStargz | SOCI | zstd:chunked | Nydus |
|---|---|---|---|---|
| Модификация образа | Да | **Нет** | Да | Да (или ZRAN: нет) |
| Индекс | Внутри слоя (JSON, последний tar entry) | Отдельный OCI artifact (FlatBuffers) | Внутри слоя (zstd skippable frame) | Отдельный bootstrap blob |
| Механизм runtime | FUSE on-demand | FUSE + background fetch | Selective pull (не FUSE) | FUSE / virtiofs / **EROFS kernel** |
| Granularity | Per-file (отдельный gzip member) | Per-span (~4 МБ) | Per-file/chunk | Per-chunk (1 МБ) |
| Prefetch стратегия | Landmark profiling | Background full download | Локальная дедупликация | Chunk dedup + P2P |
| Совместимость с registry | Любой OCI | Любой OCI | Любой OCI (zstd) | Любой OCI |
| Ломает DiffID | Да | Нет | Нет | N/A (свой формат) |
| Overhead размера | +несколько % | +несколько МБ на индекс | zstd на 10-20% меньше gzip | Зависит от дедупликации |
| Порог эффективности | > 250 МБ | > 250 МБ | Любой размер (dedup) | Любой размер |
| Kernel-native path | Нет | Нет | Нет | Да (EROFS, Linux 5.19+) |
| Registry как runtime зависимость | Да | Да (до завершения background fetch) | Нет | Да (в FUSE/virtiofs режимах) |

#### Релевантность для selective vulnerability scanning

Для задачи сканирования (где нужны единичные файлы, а не 6.4% как при lazy pull) наиболее подходят:

1. **SOCI** — не трогает образ; zTOC генерируется на стороне registry при push; сканер читает zTOC → находит offsets нужных файлов → Range requests. Waste до 4 МБ на span (всё равно драматически меньше 80 МБ полного слоя). Самый практичный вариант для managed registry.

2. **eStargz** — file-level granularity (без waste на span), но требует конвертации образа при push. Менее практично для managed registry, где образы приходят извне.

3. **Nydus ZRAN** — аналог SOCI по подходу (внешний индекс), но с опциональным EROFS kernel path. Перспективно, но более тяжёлая зависимость.

4. **zstd:chunked** — не подходит: это partial pull при запуске контейнера, не selective access к произвольным файлам.

#### Актуальные открытые вопросы

- Что реально происходит с `index_state` в Clair при обновлении — можно проверить на живой инсталляции
- Насколько реален SOCI-подход для сканирования на практике: какой overhead у чтения zTOC + Range requests vs скачивание всего слоя? Нужен бенчмарк
- Какой процент слоёв в реальном registry содержит eStargz/zstd:chunked? Если близок к нулю — нужен механизм генерации индекса на стороне registry
- Для Java-анализаторов (*.jar) selective access бесполезен — нужно сканировать все jar'ы в слое. Какая доля образов в реальном registry — Java?
- SOCI span = 4 МБ waste per file access. Для сканирования это приемлемо (нужно ~5-10 файлов → ~20-40 МБ vs 80 МБ полный слой). Но для мелких слоёв выигрыш может быть нулевым — нужен порог
