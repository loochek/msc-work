\section{Экспериментальная оценка}
\label{sec:Chapter5} \index{Chapter5}

Для оценки работы разработанного прототипа была проведена серия экспериментов, в ходе которых разработанный форк Trivy с поддержкой eStargz (в дальнейшем~--- \textit{trivy-estargz}) сравнивался с тремя другими сканерами: оригинальным Trivy, Grype (в связке с Syft) и Clair. В данном разделе подробно описаны методология эксперимента, разработанный для его проведения инструментарий и полученные результаты.

\subsection{Методология бенчмарка}

Целью экспериментальной оценки являлось получение количественных показателей эффективности предлагаемого подхода в условиях, приближённых к реальному использованию. Для этого требовалось решить ряд методологических вопросов:

\begin{itemize}
\item какие образы использовать в качестве тестового набора, чтобы он отражал реальный профиль нагрузки;
\item какие именно метрики собирать в ходе сканирования;
\item как обеспечить воспроизводимость результатов.
\end{itemize}

\subsubsection{Тестовый набор образов}

В качестве модельного профиля нагрузки рассматриваетс container registry, через который проходят образы, регулярно создаваемые автоматизированными CI/CD-конвейерами. Такой сценарий обладает следующими характерными свойствами:

\begin{itemize}
\item образы строятся на основе разнообразных базовых образов~--- Ubuntu, Alpine, Fedora, специализированных образах для конкретных языков (Python, Node.js, Go);
\item образы делятся на относительно стабильную часть (базовый Linux + системные пакеты + языковые зависимости) и часто изменяющуюся часть (приложение);
\item один и тот же образ публикуется в registry в различных версиях с одинаковым набором зависимостей, но разной версией самого приложения~--- что моделирует обновления приложения при неизменных зависимостях.
\end{itemize}

Для воспроизводимости результатов тестовый набор образов генерируется автоматически по описанному выше шаблону. Параметрами генерации являются:

\begin{itemize}
\item \textit{количество производных образов на базовый}~--- сколько различных образов на каждом базовом дистрибутиве сгенерировать (в наших экспериментах~--- 5);
\item \textit{количество версий каждого производного}~--- сколько <<коммитов>> сэмулировать для каждого производного образа (в наших экспериментах~--- 3).
\end{itemize}

С такими параметрами генерируется $6 \times 5 \times 3 = 90$ образов, покрывающих следующие типы:

\begin{itemize}
\item \texttt{ubuntu:22.04} + apt-пакеты;
\item \texttt{alpine:3.18} + apk-пакеты;
\item \texttt{fedora:39} + dnf-пакеты;
\item \texttt{python:3.11-slim} + apt-пакеты + pip-пакеты;
\item \texttt{node:20-slim} + apt-пакеты + npm-пакеты;
\item \texttt{golang:1.23} с дальнейшей упаковкой Go-бинарного файла в \texttt{scratch}-образ.
\end{itemize}

Для каждого производного образа набор устанавливаемых пакетов генерируется случайным образом из заранее заданных пулов реальных популярных пакетов (например, для apt~--- curl, vim, openssh, libssl-dev и т.п.; для pip~--- requests, flask, numpy и т.п.). Это обеспечивает реалистичный набор зависимостей в каждом образе.

Случай Go-образа заслуживает отдельного внимания: чтобы получить реалистичный образ с метаинформацией о модулях, вшитой в исполняемый файл, используется multi-stage сборка~--- сначала исходный файл собирается во временный build-контейнер на базе \texttt{golang:1.23}, затем готовый исполняемый файл переносится в \texttt{scratch}-образ.

Для каждого образа также генерируются разные версии приложения (различные исходные файлы), что обеспечивает разные верхние слои при общем составе зависимостей.

\subsubsection{Метрики}

В рамках бенчмарка с каждого сканера для каждого образа собираются следующие метрики:

\begin{itemize}
\item \textit{wall\_time}~--- полное время сканирования образа (от запуска до получения отчета);
\item \textit{index\_time}~--- время индексирования (там, где это разделение явно выражено~--- для Grype это время работы Syft, для Clair~--- время работы indexer);
\item \textit{match\_time}~--- время сопоставления с базой уязвимостей;
\item \textit{vulns}~--- количество найденных уязвимостей по уровням критичности (Critical, High, Medium, Low, Other);
\item \textit{layers\_fetched}~--- список дайджестов слоев, скачанных из registry в ходе сканирования;
\item \textit{layers\_cached}~--- список дайджестов слоев, взятых из локального кеша;
\item для trivy-estargz дополнительно~--- \textit{bytes\_fetched}: для каждого слоя~--- реальный объем скачанных из registry данных, замеренный счётчиком внутри range-загрузчика, ответственного за выполнение HTTP Range-запросов к registry.
\end{itemize}

\subsubsection{Условия запуска и воспроизводимость}

Все сканеры запускались на одной и той же машине, в одной и той же сети относительно registry. Перед запуском каждого сканера его локальный кеш слоёв полностью очищался, чтобы все слои образа гарантированно скачивались из registry, и измерения отражали \textit{наихудший} с точки зрения скорости сценарий~--- т.е. сценарий, в котором эффект от использования eStargz проявляется наиболее ярко.

Базы уязвимостей загружались для каждого сканера предварительно перед началом эксперимента.

\subsection{Разработка тестового фреймворка}

Для проведения описанных экспериментов был разработан фреймворк, состоящий из набора скриптов, реализующих следующие шаги:

\begin{itemize}
\item генерация и загрузка тестового набора образов в registry;
\item конвертация всех образов из тестового набора в формат eStargz и их загрузка в registry под отдельным тегом-суффиксом;
\item runner бенчмарка, выполняющий сканирование всех образов всеми указанными сканерами и собирающий метрики;
\item верификация корректности~--- попарное сравнение количества уязвимостей между обычным Trivy и trivy-estargz для каждого образа;
\item построение графиков по собранным результатам.
\end{itemize}

\subsubsection{Архитектура фреймворка}

Фреймворк построен по модели <<генерация $\rightarrow$ конвертация $\rightarrow$ сканирование $\rightarrow$ верификация $\rightarrow$ анализ>>. Каждый из шагов формирует свой артефакт, и каждый следующий принимает на вход артефакт предыдущего.

\subsubsection{Развертывание окружения}

В составе фреймворка предполагается работа со следующими внешними компонентами:

\begin{itemize}
\item \textit{container registry}~--- в качестве registry в экспериментах использовался Harbor, развернутый на отдельной машине в той же сети. Harbor выбран как наиболее распространённое open-source решение для корпоративного использования, поддерживающее как OCI-совместимое хранение, так и интеграцию со сканерами;
\item \textit{Clair}~--- развертывается отдельно в виде набора контейнеров (indexer, matcher, postgres) через \texttt{docker-compose};
\item \textit{Trivy, Grype, Syft, trivy-estargz}~--- устанавливаются локально как обычные CLI-утилиты.
\end{itemize}

\subsection{Обзор результатов и сравнение}

После прохождения всего пайплайна были собраны метрики по сканированию каждого из 90 образов всеми четырьмя сканерами. Графики ниже представляют усреднённые результаты по типу базового образа.

\subsubsection{Производительность сканирования}

На рис.~\ref{fig:perf} приведено среднее время сканирования (\texttt{wall\_time}) для каждого сканера и каждого типа базового образа.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{chart-performance.png}
    \caption{Среднее время сканирования по типу базового образа}
    \label{fig:perf}
\end{figure}

Можно заметить следующие наблюдения:

\begin{itemize}
\item \texttt{trivy-estargz} существенно быстрее обычного \texttt{trivy} на всех типах образов, кроме \texttt{golang}~--- разница в среднем составляет 4--10X;
\item \texttt{clair} оказывается сопоставим по скорости с \texttt{trivy-estargz};
\item \texttt{grype} в большинстве случаев медленнее обычного \texttt{trivy}, что объясняется отсутствием в нём кеша слоев и тем, что для каждого образа полностью производится индексирование;
\item на \texttt{golang}-образах разница между \texttt{trivy} и \texttt{trivy-estargz} существенно меньше. Причина в том, что метаинформация о Go-модулях не выносится в отдельный манифест, а вшивается компилятором непосредственно в собранный исполняемый файл. В образах с \texttt{scratch}-базой этот файл фактически и составляет всё содержимое образа, и анализатор Go-модулей вынужден запрашивать его целиком~--- ленивая загрузка по TOC в такой ситуации не даёт выигрыша. Этот сценарий в работе намеренно включен в тестовый набор как контрпример, на котором предложенный подход заведомо не работает.
\end{itemize}

Стоит отметить, что наблюдаемое ускорение \texttt{trivy-estargz} относительно \texttt{trivy} носит не линейный, а скачкообразный характер~--- при определенном пороге размера слоя время сканирования выходит на плато (несколько секунд на образ), определяемое прежде всего временем работы анализаторов и матчера на содержимом, а не сетевыми задержками. Этот эффект особенно заметен на \texttt{alpine}-образах, где обычный Trivy всё равно скачивает значительные объемы данных, в то время как \texttt{trivy-estargz} ограничивается единицами мегабайт.

\subsubsection{Корректность результатов}
\label{subsec:correctness}

Помимо производительности, не менее важной является корректность результатов сканирования. Для её верификации производилось попарное сравнение результатов обычного Trivy и trivy-estargz для каждого образа по количеству уязвимостей в разбивке по уровням критичности (Critical, High, Medium, Low, Other). По результатам верификации все 90 образов показали \textit{полное} совпадение количества уязвимостей между двумя сканерами по всем уровням критичности.

При интерпретации этого результата следует помнить про оговорку, описанную в \hyperref[sec:Chapter4]{разделе 5}: текущая реализация прототипа не обрабатывает opaque whiteout, что в общем случае может приводить к расхождениям с обычным Trivy на образах, где соответствующие записи встречаются. В использованном тестовом наборе таких образов не оказалось, поэтому отклонений зафиксировано не было; в более широком сценарии этот момент требует доработки прототипа.

\subsection{Обсуждение результатов}

Полученные результаты позволяют сделать следующие основные выводы:

\begin{itemize}
\item предложенный подход обеспечивает кратное (в среднем 4--10X) ускорение сканирования относительно обычного Trivy;
\item объём скачиваемых из registry данных снижается до 5--15\% от размера образа в большинстве случаев;
\item на тестовом наборе результаты сканирования полностью совпадают с результатами обычного Trivy. Принципиальных расхождений в работе сканера на данный момент не обнаружено, однако в текущей реализации остаётся открытым вопрос обработки opaque whiteout;
\item за это приходится платить незначительным (примерно 5\%) увеличением размера образа в формате eStargz по сравнению с обычным форматом.
\end{itemize}

При этом эффективность подхода зависит от типа сканируемого образа. Наибольший выигрыш наблюдается для образов с большим объемом языковых пакетов (особенно \texttt{node\_modules}), наименьший~--- для образов, в которых анализ требует обработки больших бинарных файлов (Go в формате scratch).

Стоит отдельно отметить, что в сравнении с другими сканерами trivy-estargz демонстрирует производительность, сопоставимую с Clair, при этом сохраняя архитектурную простоту Trivy~--- сканер по-прежнему остаётся stateless CLI-утилитой, не требующей дополнительной инфраструктуры (PostgreSQL, фоновых процессов и т.п.). Это делает предложенный подход особенно привлекательным для встраивания в существующие CI/CD-конвейеры и serverless-окружения.

\subsubsection{Ограничения экспериментальной оценки}

При интерпретации полученных результатов следует учитывать ряд ограничений:

\begin{itemize}
\item тестовый набор содержит синтетически сгенерированные образы, моделирующие типичный профиль нагрузки, но не покрывающие весь спектр реальных сценариев. В частности, в нём отсутствуют образы со специализированным содержимым (например, ML-модели, большие наборы данных и т.п.);
\item эксперимент проводился на одной паре <<сканер--registry>> в локальной сети с малыми задержками. Результаты при работе через интернет с большими задержками могут отличаться: с одной стороны, рост задержек должен сильнее влиять на trivy-estargz, поскольку он использует больше HTTP-запросов; с другой стороны, экономия суммарного объема данных перевешивает рост задержек, особенно для крупных образов;
\item базы уязвимостей разных сканеров отличаются по составу, что приводит к расхождениям в количестве найденных уязвимостей между сканерами. Это нормально и не считается ошибкой: сравнение производительности проводилось без оглядки на абсолютные значения;
\item бенчмарк проводился на сравнительно небольшом наборе образов (90 единиц). В реальной эксплуатации количество образов в registry на порядки больше, что в общем случае увеличивает влияние кеша слоев. Все запуски в данной работе проводились с чистым кешем, что соответствует наихудшему сценарию.
\end{itemize}

Несмотря на перечисленные ограничения, проведённая экспериментальная оценка позволяет сделать достаточно уверенный вывод о применимости предложенного подхода и его потенциале для практического внедрения.
